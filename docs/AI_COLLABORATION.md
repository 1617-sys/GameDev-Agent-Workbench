# AI 协作开发规范

本文档定义 GameDev Agent Workbench 的 AI 协作开发方式。它既是日常开发 SOP，也是项目向面试官证明 AI 工程能力的过程证据。

第一次按照本规范开发时，先阅读 [VIBE_CODING_TUTORIAL.md](./VIBE_CODING_TUTORIAL.md)，再回到本文查询具体规则和检查清单。

本项目所说的“完全 Vibe Coding”不是：

```text
用一句模糊需求让 AI 写完整个项目，然后只看页面能不能打开。
```

而是：

```text
人负责目标、约束、边界和验收
-> AI 读取项目上下文并提出实现计划
-> AI 在有限范围内实现
-> Harness 自动验证
-> AI 审查 diff
-> 人审查业务与工程边界
-> 根据失败证据迭代
-> 将有效规则和踩坑经验写回项目
```

核心原则：

> 不用“相信 AI”换取速度，而是用可执行约束、自动化验证和小步迭代获得速度。

## 1. 人和 AI 的职责

### 人负责

- 明确为什么做、做成什么样。
- 决定业务边界、优先级和取舍。
- 确认状态机、并发语义、事务边界和安全要求。
- 审查 AI 是否误解业务。
- 判断结果是否达到可交付标准。
- 能独立解释最终进入仓库的关键代码。

### AI 负责

- 阅读仓库并补齐技术上下文。
- 给出任务拆解、风险和受影响文件。
- 编写样板代码、测试、文档和首版实现。
- 执行构建、测试、静态检查和差异审查。
- 根据明确的失败证据定位并修复问题。
- 将重复出现的经验整理为规则或 Harness。

### 不可外包给 AI 的判断

- “这个功能到底有没有业务价值”。
- “并发时哪一个请求应该成功”。
- “失败后状态应该回滚、重试还是保留”。
- “哪些数据必须一致，哪些允许最终一致”。
- “为了赶进度可以接受哪些技术债”。

## 2. 项目事实来源

AI 每次工作前应按以下优先级理解项目，发生冲突时以上层为准：

1. 当前任务的需求契约和验收标准。
2. 仓库中的 AI 规则文件。
3. 架构、接口、数据模型等专题文档。
4. 当前分支中的代码和测试。
5. README、历史计划和旧会话记录。
6. AI 根据通用经验做出的推测。

本项目当前关键上下文：

| 内容 | 位置 |
| --- | --- |
| 项目定位和 JD 映射 | `docs/jd-capability-map.md` |
| 总体重构方向 | `docs/engineering-refactor-roadmap.md` |
| 里程碑和任务顺序 | `docs/refactor-task-breakdown.md` |
| AI 协作方式 | `docs/AI_COLLABORATION.md` |
| Java 后端 | `backend-java/` |
| Python Agent | `python-agent/` |
| Vue3 + Phaser 前端 | `frontend-vue/` |

文档不能替代代码。AI 发现文档和代码不一致时，不得擅自选择一个继续实现，必须指出差异，并在本次任务中同步修正文档或明确记录技术债。

## 3. 需求先写成契约

超过一个文件的改动，编码前都应先写一个轻量需求契约。小任务可以直接写在对话中，大任务写入 `docs/requirements/`。

### 3.1 需求契约模板

````markdown
# 功能名称

## 背景
现在发生了什么，为什么需要修改？

## 目标
本次完成后，用户或系统获得什么能力？

## 范围
- 本次要做什么。

## 非目标
- 本次明确不做什么。

## 业务流程
1. 谁发起请求。
2. 系统经过哪些状态。
3. 成功时返回什么。
4. 失败时如何处理。

## 接口与数据
- API 请求、响应和错误码。
- 新增或修改的数据表、字段、索引。
- 状态机和状态转换条件。

## 并发与异常
- 重复请求如何处理。
- 超时、重试、重复消息如何处理。
- 部分成功时如何恢复。
- 服务重启后如何继续或终止。

## 约束
- 不允许修改的模块。
- 兼容性要求。
- 是否允许新增依赖。
- 性能、安全和日志要求。

## 验收标准
- [ ] 可由测试、命令或可观察结果证明的条件。

## 验证命令
```powershell
# 本任务必须通过的命令
```
````

### 3.2 好的验收标准

验收标准必须可观察、可重复，避免使用“正常”“完善”“优雅”等无法验证的词。

不够好：

```text
增加 Redis 防重复提交，保证运行正常。
```

更好：

```text
同一用户对同一项目连续提交 10 次相同工作流时：
- 只创建 1 个有效 WorkflowRun。
- 其余请求返回固定业务错误码 WORKFLOW_ALREADY_RUNNING。
- Redis 锁带 TTL，任务异常退出后不会永久阻塞。
- 只有锁持有者可以释放锁。
- 单元测试覆盖抢锁成功、抢锁失败、过期和错误释放。
```

## 4. 如何给 AI 提供上下文

### 4.1 写入规则文件的内容

长期稳定、多个任务都会复用的约束应写入仓库，让 AI 自己读取：

- 模块职责和禁止跨越的边界。
- 代码风格、命名、统一响应和异常规范。
- 状态机合法转换。
- Redis key、TTL 和锁释放规范。
- MQ 消费幂等与重试规则。
- 数据库迁移和事务规范。
- 必须执行的测试、构建和检查命令。
- 已确认且容易重复踩到的坑。

建议后续逐步建立：

```text
AGENTS.md
docs/ARCHITECTURE.md
docs/API_CONVENTIONS.md
docs/ERROR_CODE_RULES.md
docs/WORKFLOW_ENGINE_DESIGN.md
docs/PITFALLS.md
```

其中 `AGENTS.md` 应短、硬、可执行，只保留每次任务都必须遵守的规则；本文件保留完整方法和解释。

### 4.2 直接贴给 AI 的内容

只与当前问题相关、很快失效的信息直接贴入对话：

- 当前报错堆栈。
- 失败测试输出。
- 一次请求和响应样例。
- 当前任务涉及的短代码片段。
- 线上日志、SQL 执行计划、性能数据。
- 希望 AI 审查的 diff。
- 临时产品取舍。

### 4.3 让 AI 自己读代码的场景

不要手工粘贴整个类或整个项目。以下场景应告诉 AI 目标和入口，让它搜索引用并读取实现：

- 修改已有业务流程。
- 重构跨文件逻辑。
- 判断接口是否被前端或其他服务使用。
- 查找项目现有模式和公共组件。
- 分析一个字段、枚举或方法的影响范围。

推荐指令：

```text
先不要修改。请从 DemoStreamServiceImpl 出发，搜索相关接口、调用方、
测试、Redis key 和状态枚举，说明当前链路、风险和预计修改文件。
所有结论必须引用仓库中的具体文件。
```

### 4.4 控制上下文长度

- 一次只给一个清晰目标。
- 让 AI 按入口主动检索，不要一次粘贴几十个文件。
- 长任务分为“探索、计划、实现、审查”四段。
- 每个阶段重新说明当前目标和已确认结论。
- 历史讨论只保留仍然有效的决定，其余沉淀进文档。

## 5. 任务如何拆解

按“可独立验证的业务纵切”拆解，不按 Java、Python、前端三个技术目录机械拆解。

不推荐：

```text
任务 A：写所有 Entity
任务 B：写所有 Service
任务 C：写所有页面
```

推荐：

```text
任务 1：建立 WorkflowRun 数据模型并完成持久化测试
任务 2：提交工作流并返回 PENDING runUuid
任务 3：RabbitMQ 消费任务并保证重复消息幂等
任务 4：SSE 展示 WorkflowRun 状态变化
任务 5：记录模型耗时、Token 和失败原因
```

每个子任务应满足：

- 能在一次短会话中解释清楚。
- 修改范围有明确所有权。
- 有独立验收标准。
- 失败时容易回滚或修正。
- 不依赖尚未确定的上游设计。

推荐规模：

```text
1 个任务
-> 1 个业务目标
-> 1 个主要模块
-> 少量相关文件
-> 1 组明确验证命令
-> 1 个可审查 commit
```

## 6. 每次交给 AI 的约束

根据任务选择下面的约束，不要只说“帮我实现”。

```text
实现约束：
1. 修改前先阅读现有实现、调用方和测试，并复述当前行为。
2. 只修改本任务需要的文件，不做无关重构。
3. 优先复用项目已有分层、异常和命名方式。
4. 未经说明不要新增依赖；确需新增时先说明理由和替代方案。
5. 保持现有 API 兼容；如无法兼容，明确列出影响方。
6. 数据状态更新必须说明事务边界和失败后的最终状态。
7. Redis 锁必须说明 key、value、TTL、锁所有权和释放方式。
8. MQ 消费必须考虑重复投递、并发消费、重试和死信。
9. 日志不得输出密码、Token、完整 Prompt 或用户隐私。
10. 为正常、边界和失败路径补测试。
11. 完成后运行约定 Harness，并报告真实结果。
12. 最后审查 git diff，列出剩余风险，不得声称未运行的测试已经通过。
```

## 7. 标准开发流程

### 第 0 步：建立 Baseline

开始任务前：

```powershell
git status --short
git branch --show-current
```

确认：

- 当前分支是什么。
- 工作区是否已有未提交修改。
- 哪些修改属于本任务，哪些必须保留。
- 基础 Harness 在修改前是否通过。

AI 不得覆盖、还原或格式化与当前任务无关的已有修改。

### 第 1 步：探索

要求 AI 先回答：

- 当前行为是什么。
- 请求经过哪些模块。
- 关键状态和数据在哪里保存。
- 哪些调用方会受到影响。
- 已有测试覆盖了什么。
- 最大风险是什么。

探索阶段默认不修改文件。

### 第 2 步：计划

计划必须包括：

- 预计修改文件。
- 每个文件为什么改。
- 状态或数据如何流转。
- 测试策略。
- 需要确认的假设。
- 可并行部分和依赖关系。

如果计划不能用几句话讲清楚，说明任务仍然太大，应继续拆分。

### 第 3 步：实现

要求 AI：

- 小批量修改。
- 每完成一个逻辑单元就运行相关测试。
- 优先增加测试再修复高风险 bug。
- 不顺手重构无关代码。
- 发现需求冲突时暂停扩大修改范围，先说明冲突。

### 第 4 步：Harness 验证

至少执行与修改相关的测试，再执行项目基础验证。

当前基础命令：

```powershell
cd backend-java
mvn test

cd ..\python-agent
python -m compileall app

cd ..\frontend-vue
npm run build

cd ..
docker compose config
```

随着项目完善，应将这些命令收敛为单一入口，例如：

```powershell
.\tools\verify.ps1
```

### 第 5 步：AI 自审

实现者完成后，不要立即接受结果。开启一次“只审查、不修改”的检查：

```text
请以严格代码审查者身份检查本次 git diff。
重点找行为回归、并发竞态、事务边界、空值、资源释放、API 兼容、
安全问题和缺失测试。先列问题，按严重程度排序，并引用文件和行号。
不要复述实现，不要因为代码能编译就判定正确。
```

条件允许时，让另一个没有参与实现的 Agent 审查，减少实现者对自身方案的路径依赖。

### 第 6 步：人工边界审查

人至少回答：

- 这真的是我要的行为吗？
- AI 是否悄悄扩大了范围？
- 正常路径之外会发生什么？
- 并发、超时、重试、取消和服务重启时会怎样？
- 数据库、缓存和消息状态可能不一致吗？
- 我能不能解释关键代码为什么这样写？

### 第 7 步：纠错

用“证据 + 期望 + 范围 + 回归测试”指导 AI，不用“还是不对，再改改”。

模板：

```text
当前失败证据：
- 测试：WorkflowSubmitServiceTest.shouldRejectDuplicateSubmit
- 现象：两个并发请求都创建了 WorkflowRun
- 日志/输出：...

期望行为：
- 同一 userId + projectUuid + workflowType 同时只能有一个有效运行。

修复范围：
- 仅处理提交幂等和对应测试，不重构 WorkflowRunner。

要求：
- 先解释根因。
- 给出最小修复。
- 增加能在修复前失败、修复后通过的并发测试。
- 运行相关 Harness 并审查 diff。
```

### 第 8 步：沉淀

满足以下任一条件，应更新文档、规则或 Harness：

- 同类问题出现两次。
- 问题只靠人工审查才能发现。
- 修复涉及不直观的业务约束。
- 新成员或新 Agent 很可能再次误解。
- 这项经验值得在面试中讲解。

## 8. Harness 是什么

Harness 是一套让 AI 修改后能够自动证明“项目仍然成立”的验证底座，不只是单元测试。

本项目 Harness 应逐步包含：

| 层级 | 目标 | 示例 |
| --- | --- | --- |
| 编译检查 | 代码可被解释器或编译器接受 | Maven compile、Python compileall |
| 单元测试 | 单个类和规则正确 | 状态转换、锁、输出解析 |
| 集成测试 | 组件协作正确 | MySQL、Redis、RabbitMQ、Python HTTP |
| 契约测试 | 跨服务结构没有漂移 | Java DTO 与 Pydantic Schema |
| 并发测试 | 竞态和幂等语义正确 | 重复提交、重复消费 |
| E2E | 主业务链路可用 | 提交 Workflow 到产出 Demo |
| 静态检查 | 风格和常见缺陷 | ESLint、类型检查、SpotBugs |
| 可观测性检查 | 失败能够定位 | traceId、runUuid、指标和日志 |

一个好的 Harness 需要：

- 本地可重复运行。
- 失败信息能指向问题。
- 执行时间与用途匹配。
- 不依赖人工观察页面。
- 覆盖项目最值钱、风险最高的链路。

本项目第一批 Harness 优先级：

1. Redis 防重复提交与锁所有权测试。
2. WorkflowRun 状态机测试。
3. MQ 重复消费幂等测试。
4. Java DTO 与 Python Schema 契约测试。
5. GameConfig Schema 校验。
6. 从提交任务到生成 Artifact 的集成测试。

## 9. 代码检查清单

### 9.1 通用正确性

- 是否满足每一条验收标准。
- 是否改动了无关文件或公共行为。
- 是否保留 API、数据库和配置兼容性。
- 空值、空集合、超长输入和非法枚举是否处理。
- 异常是否被吞掉或被转换成错误的成功响应。
- 资源、连接、线程和 SSE emitter 是否正确释放。
- 日志是否足够定位问题且不泄露敏感数据。

### 9.2 数据库与事务

- 唯一约束和索引是否支撑业务语义。
- 读后写是否存在并发竞态。
- 事务是否跨越慢速 LLM 或网络调用。
- 回滚后缓存、消息和数据库是否可能不一致。
- 重试是否会重复插入或重复更新。
- 状态更新是否校验旧状态，避免非法跳转。

### 9.3 Redis 与锁

- key 是否包含正确的业务维度。
- value 是否为唯一 owner token。
- 是否设置合理 TTL。
- 长任务是否需要续期。
- 解锁是否使用“比较 owner 后删除”的原子操作。
- 获取锁失败时是否错误地继续执行。
- Redis 不可用时是拒绝、降级还是继续，是否明确。
- 是否有数据库唯一约束或幂等记录作为最终防线。

### 9.4 RabbitMQ 与异步任务

- 生产消息与数据库提交之间是否可能丢消息。
- 消费者是否按业务 ID 幂等，而不是按进程内变量判断。
- ACK 时机是否正确。
- 失败是否会无限重试。
- 是否区分可重试和不可重试错误。
- 重试时是否重复调用 LLM、重复计费或重复生成 Artifact。
- 是否记录 retryCount、失败原因和最终状态。
- 服务重启后 PENDING/RUNNING 任务如何处理。

### 9.5 AI 输出

- 是否使用结构化 Schema 校验，而不是只检查字符串非空。
- PromptVersion、模型名和输入快照是否可追溯。
- 输出解析失败是否有明确状态和原始证据。
- RAG 片段来源是否可追踪。
- Mock fallback 是否会伪装成真实模型成功。
- Token、耗时、重试次数和成本是否记录。
- 不可信模型输出是否会直接进入 SQL、HTML 或命令执行。

### 9.6 前端与 SSE

- 断线重连是否重复创建任务。
- 页面刷新后是否能从服务端恢复真实状态。
- 事件是否可能乱序或重复。
- 失败、超时、取消和空数据是否有状态。
- 前端是否重复实现后端状态机。
- 组件卸载后是否关闭连接和清理监听器。

### 9.7 测试质量

- 测试是否在修复前能失败。
- 是否只测试了 Mock 的返回值，而没有测试业务状态。
- 是否覆盖正常、边界、失败和重复执行。
- 并发测试是否真的并发启动。
- 测试是否依赖执行顺序、外部个人配置或残留数据。
- 测试名称是否清楚表达业务规则。

## 10. Worktree 使用规范

Git worktree 允许同一个仓库同时拥有多个独立工作目录，每个目录检出不同分支。它适合多个 Agent 并行处理互不冲突的任务，不是每个小改动都必须使用。

### 适合使用

- 两个任务修改不同模块且可以独立验收。
- 需要保留当前脏工作区，同时开始隔离实验。
- 一个 Agent 实现，另一个 Agent 在独立分支补 Harness。
- 长期重构和紧急修复需要同时推进。

### 不适合使用

- 两个任务会大量修改同一组文件。
- 上游接口和数据模型尚未确定。
- 当前 baseline 不能构建或无法解释。
- 只是改一处文档或一个小 bug。

### 推荐流程

```powershell
# 在主工作树确认状态
git status --short
git branch --show-current

# 从稳定 baseline 创建独立分支和目录
git worktree add ..\gaw-harness -b codex/harness-foundation

# 查看所有 worktree
git worktree list

# 完成、提交并合并后再移除
git worktree remove ..\gaw-harness
git worktree prune
```

规则：

- 一个 worktree 只承担一个清晰目标。
- 一个分支不能同时被两个 worktree 检出。
- 每个 worktree 都先运行 baseline Harness。
- 不让多个 Agent 同时修改同一个文件。
- 合并顺序由依赖关系决定，不按谁先写完决定。
- 移除 worktree 前确认改动已提交或明确不再需要。

## 11. 多 Agent 编排规范

多 Agent 的价值是并行探索和隔离审查，不是让更多模型同时改更多代码。

### 推荐角色

| 角色 | 产出 | 默认权限 |
| --- | --- | --- |
| 主 Agent | 需求契约、任务图、最终集成 | 可协调全局 |
| 探索 Agent | 调用链、风险、影响范围 | 只读 |
| 实现 Agent | 一个垂直任务的代码和测试 | 限定 worktree |
| 测试 Agent | Harness 和失败用例 | 限定测试范围 |
| 审查 Agent | diff 问题清单 | 只读 |
| 文档 Agent | 架构、决策和演示材料 | 限定 docs |

### 编排步骤

1. 主 Agent 固定需求契约和接口边界。
2. 建立任务依赖图，区分可并行与必须串行。
3. 为每个 Agent 指定输入、允许修改范围和交付物。
4. 独立 worktree 中实现并运行各自 Harness。
5. 审查 Agent 检查 diff，不直接替实现者掩盖问题。
6. 主 Agent 按依赖顺序集成并运行全量 Harness。
7. 冲突由主 Agent根据业务语义解决，不能机械接受任一侧。

### Agent 任务卡模板

```markdown
## 目标
实现 RabbitMQ 消费幂等。

## 已确认契约
- 业务幂等键为 workflowRunUuid。
- SUCCESS/FAILED/CANCELED 不得再次执行模型调用。

## 允许修改
- backend-java/.../workflow/**
- 对应测试

## 禁止修改
- 前端
- Python Agent 接口
- 数据库既有字段语义

## 交付物
- 实现代码
- 重复消息测试
- 设计决定说明

## 验证
- mvn test -Dtest=WorkflowConsumerTest

## 完成定义
- 相同消息并发消费两次，只发生一次有效执行。
```

## 12. 如何引导 AI 修正

优先给 AI 原始证据，不要先替它猜根因。

有效输入：

- 完整异常类型和关键堆栈。
- 可复现步骤。
- 失败测试名称和断言差异。
- 请求 ID、workflowRunUuid 和时间线。
- 修复前后的行为对比。
- 最小相关 diff。

要求 AI 按以下顺序工作：

```text
复现或理解失败
-> 定位根因
-> 说明为什么现有 Harness 没拦住
-> 增加回归测试
-> 最小修复
-> 运行相关和基础 Harness
-> 审查是否引入新问题
```

连续两次修复仍失败时，不应继续叠补丁。应退回重新检查：

- 需求是否矛盾。
- 数据模型是否不支持目标语义。
- 是否修错层级。
- 是否存在未读取的调用方。
- 测试是否验证了错误的假设。

## 13. 踩坑沉淀规范

建议建立 `docs/PITFALLS.md`，每条记录使用统一格式：

```markdown
## Redis 锁判断反向导致未持锁请求执行

### 场景
用户通过 SSE 提交游戏 Demo 工作流。

### 错误表现
抢锁失败的请求继续执行，抢锁成功的请求没有执行。

### 根因
将 `locked == false` 错写为进入主流程的条件，且 finally 无条件删除锁。

### 固化规则
- 只有 `locked == true` 才能进入临界区。
- 锁 value 必须保存 owner token。
- 只有 owner 可以原子释放锁。

### 自动验证
- shouldExecuteWhenLockAcquired
- shouldRejectWhenLockNotAcquired
- shouldNotDeleteAnotherOwnerLock

### 关联文件或提交
- 文件路径、PR 或 commit
```

经验沉淀的三个层次：

1. `PITFALLS.md` 记录为什么会错。
2. `AGENTS.md` 固化以后必须遵守的短规则。
3. Harness 用自动化测试阻止同类错误再次进入仓库。

只有第 1 层是“记笔记”；三层都做到，才是工程能力。

## 14. 完成定义

一个任务只有同时满足以下条件才算完成：

- 需求范围和非目标明确。
- 实现满足全部验收标准。
- 正常、边界和失败路径有验证。
- 相关 Harness 与项目基础 Harness 通过。
- AI 已审查本次 diff。
- 无法消除的风险已明确记录。
- 接口、配置、架构发生变化时文档已同步。
- 新踩坑已进入 `PITFALLS.md`、规则或测试。
- 提交信息能够表达一个独立业务变化。
- 你能够不依赖 AI 解释关键设计和代码。

“页面能打开”“AI 说已经完成”“代码能够编译”都不能单独作为完成标准。

## 15. 推荐 Prompt 模板

### 探索模板

```text
目标：理解【功能/问题】，暂时不要修改文件。

请读取仓库中的相关实现、调用方、测试和文档，输出：
1. 当前业务链路。
2. 关键数据和状态变化。
3. 受影响文件。
4. 已有测试与缺口。
5. 并发、异常和兼容性风险。

不要仅根据文件名推测，结论引用具体文件。
```

### 实现模板

```text
请实现【目标】。

验收标准：
- ...

约束：
- 只修改...
- 不新增依赖。
- 保持...接口兼容。
- 必须考虑重复请求、超时和失败恢复。

流程：
1. 先读现有实现并给出简短计划。
2. 实现最小改动和回归测试。
3. 运行【验证命令】。
4. 审查 git diff，报告修改、验证结果和剩余风险。
```

### 审查模板

```text
只做代码审查，不修改文件。

检查当前任务的 git diff，优先寻找：
- 不满足验收标准的行为。
- 状态机和事务错误。
- 并发竞态与幂等缺陷。
- 超时、重试、重复消费和资源释放问题。
- API/Schema 兼容性回归。
- 安全和敏感信息问题。
- 缺失或无效测试。

先列发现，按严重程度排序；每条引用文件和行号，
说明触发条件、影响和建议修复方向。没有问题也要说明残余风险。
```

### 调试模板

```text
请根据以下证据定位根因，先不要猜测性改代码：

复现步骤：
...

期望：
...

实际：
...

测试/日志/堆栈：
...

要求先说明根因和影响范围，再增加能稳定复现的测试，
最后做最小修复并运行相关 Harness。不要顺手重构无关模块。
```

## 16. 本项目的示范闭环

以“工作流防重复提交”为例：

```text
需求契约
-> 定义同一 userId + projectUuid + workflowType 的并发语义

-> 将锁规范提炼到 AGENTS.md
```

这条链路同时证明：

- Java 业务设计能力。
- Redis 与并发控制能力。
- Harness 和代码审查能力。
- AI 协作与知识沉淀能力。
- 能够把一次 bug 变成长期工程资产。

## 17. 每日执行节奏

每天开始：

1. 只选择一个可验收的纵切任务。
2. 写 10 到 30 行需求契约。
3. 让 AI 探索代码并提出计划。
4. 删除计划中暂时不需要的范围。
5. 建立或确认 baseline Harness。

开发过程中：

1. 小步实现。
2. 失败先留证据。
3. 每个重要规则都用测试表达。
4. 不让多个 Agent 同时争夺同一文件。

结束前：

1. 跑 Harness。
2. 审查 diff。
3. 检查验收标准。
4. 更新 PITFALLS 或架构文档。
5. 形成一个可解释的 commit。
6. 用自己的话复述今天的设计决定。

最终目标不是让 AI 替你写更多代码，而是让每一次 AI 生成都处在一个可理解、可验证、可纠正、可沉淀的工程系统中。
