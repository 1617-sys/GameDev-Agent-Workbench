# Vibe Coding 小白开发教程

> 适用项目：GameDev Agent Workbench
>
> 目标读者：第一次使用 Codex 做完整工程重构的开发者
>
> 核心策略：少量高质量任务，而不是大量模糊对话

本教程回答：

1. `README.md` 和 `AI_COLLABORATION.md` 分别怎么用。
2. 每天打开 Codex 后第一句话应该说什么。
3. 怎样把一个大重构拆成不会失控的小任务。
4. 怎样检查 AI 写的代码，而不是直接相信它。
5. 怎样在 Plus 有限额度下完成整个项目。

---

## 1. 先理解两份文档的分工

### `README.md` 是项目地图

[README.md](./README.md) 回答：

```text
项目现在是什么
-> 最终要变成什么
-> 为什么要这样改
-> 应该先做哪一阶段
-> 每一阶段怎样验收
```

你不需要每天从头读完。开发某个阶段时，只阅读：

- 第 1 节：改造需求契约。
- 第 2 节：当前现状。
- 当前阶段，例如 `R0`。
- 与任务有关的专题，例如 Redis、Workflow、RAG。

### `AI_COLLABORATION.md` 是开发操作规程

[AI_COLLABORATION.md](./AI_COLLABORATION.md) 回答：

```text
怎样描述需求
-> 怎样给 AI 上下文
-> 怎样限制修改范围
-> 怎样运行 Harness
-> 怎样审查代码
-> 怎样纠错
-> 怎样沉淀踩坑
```

简单记忆：

```text
README = 做什么
AI_COLLABORATION = 怎么做
当前任务卡 = 这一次具体做什么
```

Codex 不应该每次自由发挥，而应该同时受到这三层约束。

## 2. 你的最低成本开发模式

Plus 额度有限时，默认使用：

```text
一个任务
+ 一个 Codex 线程
+ 一个 Agent
+ 一个主要模块
+ 一组验收标准
+ 一次最终全量验证
```

默认不要：

- 同时启动多个 Agent。
- 同时创建多个 worktree。
- 一句话要求“完成 R0”或“重构整个项目”。
- 每次都让 Codex 重新分析整个仓库。
- 在一个线程里连续开发多个无关功能。
- 代码还没验证就让 Codex继续增加功能。
- 为了显得工程化而一次引入多个中间件。

OpenAI 官方说明，Codex 消耗与任务规模、复杂度、代码库大小和会话需要保持的上下文有关；简单任务消耗较少，大型代码库、长任务和长上下文会消耗更多。因此，最有效的节省方式不是少写几个字，而是缩小每次任务的实际范围。[官方说明](https://help.openai.com/en/articles/11369540-using-codex-with-chatgpt)

## 3. 第一次开始前的准备

### 3.1 只确认当前阶段

目前只做：

```text
R0：固定 Baseline 与修复高风险缺陷
```

不要提前让 Codex 实现 RabbitMQ、RAG 或 Prompt 实验。

### 3.2 查看 Git 状态

在项目根目录运行：

```powershell
git status --short
git branch --show-current
git worktree list
```

你需要知道：

- 当前在哪个分支。
- 哪些文件已经修改。
- 哪些修改是你自己的。
- 是否有不能被 Codex 覆盖的内容。

如果输出看不懂，可以只把 `git status --short` 的输出交给 Codex解释，不要立即让它清理。

### 3.3 不急着使用 worktree

作为小白，前几个任务只在当前 `refactor-v2` 分支顺序开发。

满足以下条件后才开始学习 worktree：

- 当前工作区已经干净或所有修改都能解释。
- `tools/verify.ps1` 已建立。
- 你能独立看懂 `git status`、`git diff` 和 commit。
- 确实存在两个互不修改相同文件的任务。

## 4. 什么是任务卡

任务卡是一次 Codex 会话的完整合同。

一张任务卡只做一件事，例如：

```text
建立一键验证脚本
修复 Redis 锁
增加 Workflow 状态机测试
增加 GameConfig 契约测试
```

不要写：

```text
帮我把项目工程化。
```

### 4.1 最小任务卡模板

````markdown
# 任务编号和名称

## 背景
当前问题是什么？

## 目标
完成后新增或修复什么能力？

## 范围
- 允许修改什么。

## 非目标
- 明确不做什么。

## 约束
- 不新增依赖。
- 不修改无关业务代码。
- 保留现有接口。

## 验收标准
- [ ] 可以通过命令或测试证明的条件。

## 验证命令
```powershell
# 本任务必须通过的命令
```
````

### 4.2 为什么任务卡能省额度

没有任务卡时，Codex 需要：

- 猜测目标。
- 搜索大量无关文件。
- 反复询问或返工。
- 在长上下文中记住不断变化的要求。

有任务卡时，Codex 只需：

- 读取指定文档。
- 搜索相关实现。
- 完成一个目标。
- 执行指定验证。

一次写清楚，比连续发送十条补充要求更省额度。

## 5. 一个五小时额度窗口怎样使用

不要把“五小时窗口”理解为必须连续使用五小时。把它理解为一次完整任务周期。

### 5.1 窗口开始前：你自己做

不消耗 Codex 额度的准备：

1. 从 `README.md` 选择当前阶段的一项任务。
2. 使用模板写出任务卡草稿。
3. 运行 `git status --short`。
4. 收集现有报错或失败输出。
5. 确认今天只做这一件事。

时间建议：15 到 30 分钟。

### 5.2 第一次 Codex 交互：完成主体工作

低风险任务直接使用“一次完成 Prompt”：

```text
请执行任务 R0-01。

开始前读取：
- docs/README.md 中“R0：固定 Baseline”部分
- docs/AI_COLLABORATION.md 中第 6、7、8、14 节
- 当前任务卡

目标：
建立 tools/verify.ps1，统一运行 Java、Python、Vue 和 Docker Compose 基础验证。

范围：
- tools/verify.ps1
- 必要的简短使用说明

非目标：
- 不修改业务逻辑
- 不新增依赖
- 不修复验证中发现的业务问题

验收：
- 任一子命令失败时脚本返回非 0
- 输出能指出失败模块
- 支持 quick profile
- 在当前项目真实运行

请先用不超过 8 行说明计划，然后直接实现、运行验证、审查 diff。
最终只报告修改文件、真实验证结果和剩余问题。
```

这一条 Prompt 已包含：

- 上下文入口。
- 目标。
- 范围。
- 非目标。
- 验收。
- 输出格式。

不要再额外发送“继续”“你看着办”“帮我完善”等模糊消息。

### 5.3 第二次交互：只处理证据明确的问题

如果测试失败，发送：

```text
继续当前任务，不扩大范围。

失败证据：
- 命令：
- 错误：
- 期望：

请先说明根因，再做最小修复。
修复后只运行相关测试和最终 quick Harness。
```

不要只说：

```text
报错了，你再看看。
```

### 5.4 第三次交互：风险审查

低风险文档、脚本、小样板代码可以由你自行检查，不必额外使用一次 AI 审查。

以下高风险任务必须审查：

- Redis 锁。
- 数据库迁移。
- Workflow 状态机。
- RabbitMQ 消费者。
- 事务和重试。
- 鉴权和安全配置。

审查 Prompt：

```text
只审查当前任务 diff，不修改文件。

根据任务卡的验收标准，重点检查：
- 是否扩大修改范围
- 并发与幂等
- 失败和资源释放
- API/数据兼容
- 测试是否真的能暴露问题

只列真实问题，按严重程度排序并引用文件和行号。
没有问题时说明残余风险，不要复述代码。
```

### 5.5 窗口结束

你自己完成：

```powershell
git status --short
git diff --stat
git diff
```

确认：

- 修改文件符合任务范围。
- 没有密码、Token、`.env` 等敏感信息。
- 验证命令确实运行过。
- 你能用自己的话说明改了什么。

然后形成一个独立 commit。不要在同一个 commit 混入下一个任务。

## 6. 不同风险任务使用不同对话次数

### 6.1 低风险：一次交互

适用：

- 文档。
- 脚本。
- DTO/VO 样板。
- 明确的小范围 UI。
- 单个测试补充。

流程：

```text
读取指定上下文
-> 简短计划
-> 实现
-> 验证
-> 自审
```

### 6.2 中风险：两次交互

适用：

- Service 小范围重构。
- API 修改。
- 前端状态拆分。
- Python Schema 修改。

流程：

```text
第一次：探索 + 计划，不修改
第二次：按确认计划实现 + 验证
```

### 6.3 高风险：三次交互

适用：

- Redis 并发。
- RabbitMQ。
- Outbox。
- 数据库迁移。
- 状态机。
- 安全。

流程：

```text
第一次：探索、调用链、风险、测试方案
第二次：先写失败测试，再最小实现
第三次：独立审查和修复
```

额度不足时，不要降低高风险任务的验证标准。正确做法是让一个任务跨两个刷新窗口完成。

## 7. 怎样告诉 Codex 读取两份文档

### 错误方式

```text
请读取项目所有文档，然后开始重构。
```

这会让 Codex 读取大量历史内容，增加上下文和冲突。

### 正确方式

```text
本次只做 R0-02 Redis 锁测试与修复。

请读取：
- docs/README.md 的“现状审计”“R0”部分
- docs/AI_COLLABORATION.md 的“每次交给 AI 的约束”
  “标准开发流程”“Redis 与锁”部分
- DemoStreamServiceImpl
- RedisService 及相关配置和测试

不要读取历史 week 计划，不处理 RabbitMQ、RAG 和前端。
```

原则：

- 指定文档章节，而不是要求读完整 docs。
- 指定代码入口，让 Codex 自己搜索调用方。
- 明确不需要读取和实现的内容。
- 一个任务只提供相关上下文。

## 8. R0 阶段的实际开发顺序

### R0-01：一键 Harness

目的：

> 以后每次 AI 修改后，都有统一命令证明项目有没有坏。

允许修改：

```text
tools/verify.ps1
README 或验证说明
```

禁止：

```text
顺手修复业务 bug
升级依赖
重构目录
```

验收：

- Java 测试可运行。
- Python 编译检查可运行。
- Vue build 可运行。
- Compose config 可运行。
- 任一步骤失败，脚本整体失败。

### R0-02：Redis 锁测试与修复

目的：

> 用测试证明只有抢锁成功的请求可以执行，并且不能释放别人的锁。

建议分成两个额度窗口。

窗口 A：

```text
只探索和写失败测试，不修复实现。
```

窗口 B：

```text
根据失败测试做最小修复，运行相关测试和 quick Harness。
```

验收：

- 抢锁成功才执行。
- 抢锁失败被拒绝。
- owner 才能释放。
- 锁有 TTL。
- 空 userId 不构造业务 key。

### R0-03：Workflow 状态测试

目的：

> 固定当前同步 Workflow 的成功与失败行为，为后续 Runner 重构提供保护。

优先测试：

- 创建时为 `RUNNING`。
- 所有步骤成功后为 `SUCCESS`。
- 任一步骤失败后为 `FAILED`。
- 错误信息和耗时被记录。
- 非项目所有者不能运行。

本任务不抽取新 Runner。

### R0-04：GameConfig 契约测试

目的：

> 防止 AI 生成“看起来像 JSON、实际上 Phaser 不能运行”的配置。

优先测试：

- 必填字段。
- 不支持的 runtime 类型。
- 数值范围。
- 多余危险字段。
- 默认配置样例。
- Java/Python/前端对同一 Schema 的理解。

### R0-05：安全配置清理

目的：

> 去掉真实项目不能接受的默认密码、JWT secret 和敏感日志。

验收：

- Secret 从环境变量读取。
- example 文件只放占位符。
- 缺少必要 Secret 时启动明确失败。
- 日志不打印 Token、密码和 API Key。

完成 R0 后才进入 R1。

## 9. 你怎样检查 AI 写的代码

你不需要一开始就能看懂每一行，但必须会做五层检查。

### 第一层：文件范围

运行：

```powershell
git diff --stat
git status --short
```

问题：

- 为什么这个任务修改了这些文件？
- 是否出现任务范围之外的文件？
- 是否修改了 `.env`、构建产物或 IDE 文件？

### 第二层：验收标准

逐条对照任务卡：

```text
验收 1 是否有测试或命令证明？
验收 2 是否只是 AI 口头声称？
失败路径是否验证？
```

### 第三层：测试真实性

检查：

- 测试在修复前是否会失败。
- 测试是否只验证 Mock。
- 是否覆盖正常、失败和边界。
- 并发测试是否真的同时启动。

### 第四层：关键代码解释

要求 Codex：

```text
请只解释本次 diff 中最关键的 3 个设计决定：
1. 为什么这样实现。
2. 不这样做会出现什么问题。
3. 对应测试在哪里。

不要逐行复述代码。
```

然后你自己尝试复述。如果复述不了，先不要进入下一个任务。

### 第五层：运行结果

区分：

```text
“应该能通过”
“AI 说已经通过”
“终端真实执行并返回 0”
```

只有第三种可以作为验收证据。

## 10. AI 写错后怎样修

### 10.1 先保留失败证据

不要立刻删除代码或大改。记录：

- 执行命令。
- 完整错误类型。
- 关键堆栈。
- 输入。
- 期望。
- 实际结果。

### 10.2 使用最小纠错 Prompt

```text
不要扩大任务范围。

失败命令：
...

关键错误：
...

期望：
...

当前实际行为：
...

请：
1. 先定位根因。
2. 说明为什么现有测试没有阻止它。
3. 增加回归测试。
4. 做最小修复。
5. 只运行相关测试和 quick Harness。
```

### 10.3 两次仍未修好

停止继续打补丁，发送：

```text
连续两次修复仍失败。暂停修改。

请重新检查：
- 需求假设
- 调用链
- 数据模型
- 测试是否验证了错误目标
- 是否在错误层级修复

只输出新的根因分析和候选方案，不修改文件。
```

## 11. 如何跨额度刷新继续任务

不要依赖一个无限增长的聊天线程。

每个任务结束或额度将耗尽前，把状态写入任务卡：

```markdown
## 当前状态
- 已完成：
- 未完成：
- 修改文件：
- 已运行验证：
- 当前失败：
- 下一步唯一动作：
- 禁止重复尝试：
```

新窗口使用：

```text
继续任务 R0-02。

请先读取：
- 对应任务卡的“当前状态”
- 当前 git diff
- 上次失败测试

不要重新分析整个项目，不重复已完成工作。
下一步唯一动作是：...
```

这种方式比让一个线程保存整个项目历史更稳定，也更省上下文。

## 12. Worktree 小白教程

### 12.1 它到底是什么

一个 Git 仓库默认只能在一个目录打开一个分支。

Worktree 允许：

```text
主目录       -> refactor-v2
另一个目录   -> codex/harness-foundation
第三个目录   -> codex/frontend-run-center
```

每个目录有独立文件，但共享同一个 Git 仓库历史。

### 12.2 什么时候才使用

例如：

- 后端 Agent 修改 `backend-java/`。
- 前端 Agent 修改 `frontend-vue/`。
- 两者依赖的 API 已经确定。

不要在以下情况使用：

- 你还不会判断 Git 改动属于谁。
- 两个任务都修改同一个 Workflow 类。
- 数据模型还没确定。
- 只是为了体验多 Agent。

### 12.3 基础命令

```powershell
git worktree add ..\gaw-harness -b codex/harness-foundation
git worktree list
```

完成并合并后：

```powershell
git worktree remove ..\gaw-harness
git worktree prune
```

不要手工删除 worktree 目录。

### 12.4 Plus 额度下的建议

多 Agent 会让多个任务同时读取上下文、思考和验证。它主要节省现实时间，不一定节省使用额度。

因此本项目默认：

```text
R0-R3：单 Agent 顺序开发
R4 之后：只有前端与评测等写入范围分离时才考虑并行
```

## 13. 模型和推理强度怎样选择

本项目只使用两档，减少选择成本：

```text
默认使用 gpt-5.4
只有任务明确标记为高风险时才切换 gpt-5.5
```

### 使用 `gpt-5.4`

适合大多数日常开发和重复工作：

- 搜索文件和梳理普通调用链。
- 更新文档和任务卡。
- 编写验证脚本。
- DTO、VO、Entity、Mapper 等样板代码。
- 普通 Controller、Service 和前端组件。
- 按已经确定的设计搬运或拆分代码。
- 增加常规单元测试。
- 根据明确报错做局部修复。
- 运行 Harness、整理测试报告。
- R0-01、R0-03、R0-04 的主要工作。
- R4 前端页面和 Store 拆分。
- R7 文档、演示脚本和报告。

### 使用 `gpt-5.5`

只用于需要深入推理、出错代价较高的任务：

- Redis 锁、限流和并发竞态。
- Workflow 状态机和合法状态转换。
- 数据库迁移、唯一约束和事务边界。
- Workflow Runner 核心抽象。
- RabbitMQ 幂等、重试、DLQ 和 Outbox。
- 服务崩溃后的任务恢复。
- PromptVersion 快照一致性。
- Java、Python、前端之间的关键契约设计。
- RAG 隔离、检索证据和评测方案。
- 鉴权、安全配置和敏感信息审查。
- 上述高风险代码的最终 diff 审查。

### 同一任务怎样切换

高风险任务也不需要从头到尾都用 `gpt-5.5`：

```text
gpt-5.5：分析风险、确定设计和验收边界
-> gpt-5.4：按确定方案编写重复实现和测试样板
-> gpt-5.5：只审查关键 diff
```

为了进一步节省额度：

- 普通任务不要使用 `gpt-5.5`。
- 不因为测试失败就立刻切换模型，先提供明确失败证据给 `gpt-5.4`。
- 只有根因涉及并发、状态、事务或跨服务契约时再升级到 `gpt-5.5`。
- 模型选择不能代替任务拆分；一个模糊大任务即使用 `gpt-5.5` 也会浪费额度。

具体可用模型和额度以 Codex 的 Usage 页面和模型选择器为准，不在项目文档中写死额度数字。

## 14. 最省额度的 Prompt 写法

一个高效 Prompt 包含七件事：

```text
任务编号
文档入口
代码入口
目标
范围与非目标
验收标准
验证和输出要求
```

### 推荐

```text
执行 R0-03，只固定 Workflow 当前行为。
读取 README 的 R0、AI_COLLABORATION 的测试与审查章节，
从 WorkflowServiceImpl 和现有测试开始搜索。

只允许修改 Workflow 相关测试和必要测试配置。
不抽 Runner，不接 MQ，不修改前端。

覆盖成功、步骤失败、无权限三个场景。
运行指定测试，最后审查 diff。
```

### 不推荐

```text
看看我的 Workflow 有什么问题，全部优化一下。
```

### 进一步节省

- 不要把 AI 可以自己读取的完整代码粘贴进 Prompt。
- 不要重复粘贴两份长文档，只给路径和章节。
- 不要在同一条消息讨论五个候选方案。
- 不要要求长篇解释，要求“计划不超过 8 行”。
- 不要让 AI 每次输出所有文件完整内容。
- 要求只报告 diff、验证结果和风险。
- 测试先跑目标模块，任务结束再跑一次完整 quick Harness。

## 17. 你现在应该做什么

现在不要继续设计更多架构，也不要启动多个 Agent。

第一步是创建并执行：

```text
R0-01：一键 Harness
```

你可以直接向 Codex 发送：

```text
请按照 docs/VIBE_CODING_TUTORIAL.md 的低额度流程执行 R0-01。

只建立一键验证入口，不修改业务逻辑，不修复检查中发现的问题。
计划不超过 8 行，然后直接实现、真实运行、审查 diff。
```

这就是整个重构的正确起点：

```text
一张任务卡
-> 一次小改动
-> 一组真实证据
-> 一次独立提交
-> 再进入下一张任务卡
```

当这个节奏形成习惯后，你的 Vibe Coding 能力就不再取决于“会不会写神奇 Prompt”，而取决于能否持续控制范围、验证结果和积累工程知识。
