# V3-04：原型版本、调参与对比

> 状态：`DONE`
>
> 前置任务：`V3-03`
>
> 推荐模型：`gpt-5.5` 并发设计，`gpt-5.4` CRUD 与页面实现
>
> 预计工时：10-14 小时

## 目标

建立不可变 PrototypeVersion，让用户调整少量白名单参数生成新版本，并比较两个版本的配置差异，为后续试玩指标建立稳定归属。

## 范围

- 按 RFC 落地 PrototypeVersion 数据模型、迁移、服务和 API。
- AI 首次生成形成版本 1；人工调参形成带父版本的新版本。
- 支持时限、玩家速度、生命、敌人数量/速度和目标数量等白名单参数。
- 服务端重新校验完整 GameConfig，客户端不能只提交任意 JSON Patch。
- 版本列表、详情、选择试玩和两版本关键参数对比。
- 创建版本具备幂等、项目归属校验和并发版本号测试。

## 非目标

- 不做可视化关卡编辑器、任意 JSON 编辑器和版本合并。
- 不允许修改已存在版本。
- 不实现 Git 式分支、复杂审批和发布流水线。
- 不实现试玩指标聚合。

## 约束

- 已创建版本及其 GameConfig 内容不可变。
- 版本号由服务端分配，并发请求不能产生同项目重复版本号。
- 白名单参数具有服务端上下限；未知字段拒绝。
- 所有查询和创建操作校验项目所有权。
- 幂等重放返回同一结果，不重复创建版本。

## 验收标准

- [x] AI 产物可形成第一个不可变原型版本。
- [x] 白名单调参创建子版本，旧版本内容保持不变。
- [x] 并发和幂等测试证明不会产生重复逻辑版本。
- [x] 用户可以选择任意历史版本试玩。
- [x] 两个版本可以比较关键参数和来源。
- [x] 越权、越界和未知字段被拒绝。

## 审查清单

- 是否原地更新导致历史试玩数据失去对应配置。
- 是否信任客户端版本号或完整配置。
- 并发创建是否存在先查后写竞态。
- 幂等响应是否可能指向不同版本。

## 完成定义

- 不可变版本、调参、对比和并发测试全部通过。
- UI 不暴露任意 JSON 或危险字段编辑能力。
- 每次试玩都可以明确绑定一个版本 UUID。
