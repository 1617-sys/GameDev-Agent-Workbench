# 第二周任务优先级拆分

这份文档不按日期排任务，而是按“技术含量”拆分。

目的很直接：

1. 避免后面一直陷在重复 CRUD 里，做了很多接口却没有明显成长。
2. 帮你区分哪些任务适合快速完成，哪些任务值得重点投入。
3. 让第二周既能推进进度，又能保留项目的 AI 味和工程辨识度。

---

## 一眼结论

第二周后面的任务可以分成两列：

- 第一列：偏 CRUD，适合快速完成，用来补齐系统结构和演示链路。
- 第二列：真正有技术含量，值得重点投入，用来拉高项目含金量。

你的策略不应该是“所有功能平均用力”，而应该是：

```text
基础 CRUD 足够完整
-> 挑 2 到 4 个高含量点做深
-> 能在面试里讲清楚链路、状态、异常和设计取舍
```

---

## 第一列：偏 CRUD，适合快速完成

这些任务主要价值是把系统补完整、把演示做顺。不是没用，但技术挑战相对低。

- `game_project` 的标准 CRUD
- `agent_run` 的列表、详情、按项目查询
- `agent_artifact` 的基础表结构和 CRUD
- 项目基础信息编辑
- 项目状态字段维护
- 按 `agentType`、`status`、`projectUuid` 做普通筛选
- 分页查询
- README、Apifox、数据库文档整理
- 响应结构统一
- 基础日志补全
- 基础异常处理补全
- Python mock 接口继续扩充
- 简单的数据看板，比如“项目数量”“执行次数”

### 这类任务的特点

- 路径比较固定
- 分层写法比较重复
- 大多是单表或简单条件查询
- 对简历有帮助，但不太能体现复杂业务处理能力

### 适合怎么做

- 赶进度时优先做
- 可以适当借助 AI 起草模板代码
- 重点保证接口通、数据库字段对、Apifox 能演示

---

## 第二列：真正有技术含量，建议重点投入

这些任务更值得你花时间。它们更接近“业务系统 + AI 工具流”的真实难点。

- `agent_run` 绑定 `project`
- 一个项目下的多步 Agent 工作流
- `agent_artifact` 作为项目产物沉淀，而不是只存 `output_content`
- Java 调真实模型 API，而不是 mock
- 结构化 JSON 输出约束与失败重试
- Agent 执行状态流转设计
- 事务处理和执行一致性
- 超时、失败、重试机制
- 项目级上下文拼装
- 按项目聚合历史执行结果
- 复杂 SQL：统计、分组、最近一次结果、失败次数排行
- 项目权限隔离：只能访问自己的项目和产物
- SSE 流式输出
- 多步骤链路编排
- RAG
- LangGraph 或类似工作流编排
- 文件上传后交给 Agent 处理
- 从“单次请求”演进到“项目工作台”

### 这类任务的特点

- 不是单表 CRUD
- 会涉及多表关系、状态变化、异常路径
- 需要真正理解链路，而不是只把代码拼起来
- 更接近 AI 产品和真实后端系统的交叉地带

---

## 当前项目里的 AI 部分到底在哪

你的项目已经有 AI 部分，只是现在处在“AI 工程链路阶段”，还不是“强模型能力阶段”。

你现在已经做出来的 AI 部分主要是：

- `Java -> Python FastAPI` 的跨服务调用
- `AgentType -> 不同 Agent 能力` 的路由分发
- `agent_run` 作为 AI 执行记录表
- Python 端返回结构化结果
- Java 端保存输入、输出、状态、耗时、错误信息

这意味着你的项目已经不是普通管理系统，而是：

```text
用户发起一次智能任务
-> Java 编排调用 Agent
-> Python 返回结构化结果
-> 系统保存执行记录
-> 用户查询历史结果
```

### 但它现在还不算“强 AI 项目”

原因不是没有 AI，而是：

- 现在的 Python 还是 mock
- 还没有真实模型 API
- 还没有多步工作流编排
- 还没有上下文记忆和产物复用

所以当前更准确的定位是：

- AI 工程链路型项目
- 不是 AI 算法能力型项目

这对实习阶段其实是合理的，因为很多岗位更看重你能不能把 AI 接进业务。

---

## 最值得深做的 4 个点

如果你没有很多时间，不要平均发力，优先把下面 4 个点做深：

1. `agent_run` 和 `project` 绑定
2. 真实模型 API 接入
3. `agent_artifact` 产物沉淀
4. 多步 Agent 工作流

这 4 个点做出来，你的项目就会从：

```text
Java 调 Python 的 demo
```

升级成：

```text
面向游戏开发场景的 AI 工具流后端平台
```

---

## 推荐投入顺序

### 第一梯队：最该优先做

- `agent_run` 绑定 `project`
- 项目下查询 `agent_run`
- `agent_artifact` 表和保存逻辑
- 真实模型 API 替换 mock
- 多步工作流：需求拆解 -> API 设计 -> Prompt 生成

### 第二梯队：可以接着做

- 结构化输出校验
- 重试机制
- 聚合查询和复杂 SQL
- SSE 流式返回

### 第三梯队：时间够再冲

- RAG
- LangGraph
- 文件上传
- 更复杂的前端工作台

---

## 哪些代码建议自己写

这些代码最值得自己手写一遍：

- DTO 字段设计
- Service 主业务流程
- 资源归属校验
- 状态流转逻辑
- Java 根据类型分发调用 Python
- 数据库字段设计和 SQL
- Apifox 测试用例
- 多步骤工作流主链路

这些可以让 AI 先起草，你再读懂和调整：

- Entity 基础字段
- VO 转换代码
- Mapper 接口
- Controller 基础接口
- README 接口说明
- 示例 JSON

---

## 面试里的价值差异

如果你只完成第一列，项目会完整，但更像一个“有 AI 字样的管理系统”。

如果你完成第一列里的基础项，再把第二列里 2 到 4 个点做深，面试里就能讲：

- 为什么需要 `project -> run -> artifact` 这条链路
- 为什么状态不能只存一个字符串
- 为什么模型输出要做结构化约束
- 为什么执行失败后要保留运行记录
- 为什么项目上下文会影响 Agent 结果

这类表达会明显更像真实工程项目。

---

## 第二周建议策略

最推荐的做法不是“所有功能都做”，而是：

```text
先把 CRUD 做到足够演示
-> 再挑关键高含量点重点做深
-> 最后把链路讲清楚、写进 README、写进简历
```

你可以把这份文档当成一个提醒：

- 第一列负责把项目做出来
- 第二列负责让项目有技术辨识度

只要第二周做成这个结构，项目的质感会明显不一样。
