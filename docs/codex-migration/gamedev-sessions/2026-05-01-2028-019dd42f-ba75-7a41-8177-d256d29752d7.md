### 34. Codex

设计表这件事，学习者最容易卡住的点，不是“不会写 SQL”，而是**不知道为什么要有这张表、字段为什么这么放**。

你可以先把思路从“我要设计数据库”改成：

**我要把系统里的核心信息，稳定地存下来。**

对你这个项目来说，先不要想着一次设计得很复杂，而是先问 3 个问题：

1. 系统里有哪些“必须长期保存”的信息？
2. 这些信息是谁产生的、给谁用？
3. 它们之间是什么关系？

---

**先用业务倒推表**

你这个项目的核心流程是：

- 用户登录
- 用户选择一个 Agent
- 用户输入一段需求/日志/设定
- 系统生成结果
- 系统保存这次执行记录
- 如果是 Prompt 生成，还可能发到旧项目

那你就能很自然地推出来，最少要存这些东西：

- 谁在用系统
- 用户开启了哪些会话
- 每次 Agent 运行了什么
- Prompt 模板长什么样
- 发给旧项目的任务记录是什么

这就是为什么会有这 5 张核心表：

- `sys_user`
- `agent_session`
- `agent_run`
- `prompt_template`
- `external_task_ref`

所以学习表设计，第一步不是背模板，而是**先从业务动作里找“要存什么”**。

---

**再学会区分“表”和“字段”**

你可以这样理解：

- **表**：一种独立的业务对象
- **字段**：这个对象身上的属性

比如 `sys_user` 这张表，表示“用户”这个对象。  
那用户有哪些属性？

- `id`
- `username`
- `password`
- `role`
- `create_time`

这就是字段。

所以第二步是问：

**这个业务对象本身，最少需要哪些属性才能成立？**

不要一开始就加很多“可能以后要用”的字段。  
学习阶段最重要的是先做到：

- 字段够用
- 含义清晰
- 不重复

---

**你现在最该学的是 4 种表设计思维**

### 1. 主体表
表示“谁”或“什么东西”

比如：
- `sys_user`
- `prompt_template`

特点：
- 数据相对稳定
- 会被别的表引用

你可以把它理解成“基础档案表”。

---

### 2. 过程表
表示“发生了一次什么事”

比如：
- `agent_run`

这张表特别重要，因为它不是存“一个对象”，而是存“一次行为”。

字段就会围绕这次行为展开：
- 谁发起的
- 用了什么 Agent
- 输入了什么
- 输出了什么
- 成功还是失败
- 花了多久

这类表在业务系统里非常常见。  
你的项目里，`agent_run` 就是最核心的过程表。

---

### 3. 关联表 / 附属表
表示“给某个主流程补充信息”

比如：
- `external_task_ref`

它不是独立主角，而是附着在一次 `agent_run` 上。  
只有当你把 Prompt 发给旧项目时，它才有意义。

为什么不把这些字段直接塞进 `agent_run`？

因为不是所有 `agent_run` 都会有外部任务。  
如果硬塞进去，会让主表变臃肿，而且语义不清楚。

所以第三步要学会问：

**这是主流程的通用信息，还是某种特殊场景下的附加信息？**

如果只是附加信息，就可以考虑单独拆表。

---

### 4. 配置表
表示“系统规则”而不是“用户行为”

比如：
- `prompt_template`

它不是用户的一次操作记录，而是给系统提供可配置能力。  
所以这类表通常会有：
- 名称
- 类型
- 内容
- 启用状态
- 版本号

这类表的重点是“便于维护和切换”。

---

**对你这个项目，最好的学习路径不是直接写 SQL，而是先做这件事**

你可以给每张表先写一行中文定义。

比如：

- `sys_user`：存系统登录用户
- `agent_session`：存用户的 Agent 会话
- `agent_run`：存每次 Agent 执行记录
- `prompt_template`：存不同 Agent 的 Prompt 模板
- `external_task_ref`：存发送到旧项目的外部任务引用

如果你能先把这 5 句话写清楚，你的表设计已经成功一半了。

---

**然后再学字段怎么定**

字段设计时，建议你按这个顺序想：

1. 这条数据是谁
2. 这条数据属于谁
3. 这条数据最核心的信息是什么
4. 它的状态是什么
5. 它什么时候创建和更新

比如 `agent_run`：

1. 它是谁  
   `id`, `run_uuid`

2. 它属于谁  
   `session_id`, `user_id`

3. 核心信息是什么  
   `agent_type`, `input_text`, `output_text`

4. 状态是什么  
   `status`, `error_msg`, `score`

5. 时间信息  
   `create_time`, `update_time`

这就是一种非常实用的学习型思路。

---

**你现在要避免的 3 个常见错误**

### 1. 一开始设计得太大
比如先想着：
- 多租户
- 多团队
- 多版本工作流
- 审批流
- 权限树

这些都不是 MVP 第一阶段该考虑的。

### 2. 把所有信息都塞进一张表
比如把外部任务状态、模板内容、评分信息全塞到 `agent_run`。  
这样后面会越来越乱。

### 3. 字段为了“以后可能要用”乱加
学习阶段要练的是“克制”。  
先让表支撑当前业务闭环，再慢慢演进。

---

**如果你想从学习角度真正掌握表设计，我建议你每设计一张表都回答这 5 个问题**

1. 这张表是干什么的？
2. 它存的是“主体信息”还是“过程信息”？
3. 它和哪张表有关系？
4. 哪些字段是最核心、不能少的？
5. 如果以后需求变大，这张表容易怎么扩展？

如果你能回答出来，你就不是在“抄表结构”，而是在真正学设计。

---

**放到你这个项目里，我建议你先按这个顺序学**

1. 先设计 `sys_user`
   因为最简单，适合练手。

2. 再设计 `agent_run`
   因为这是项目最核心的表。

3. 再设计 `agent_session`
   学“会话”和“执行记录”的关系。

4. 再设计 `prompt_template`
   学“配置型表”怎么建。

5. 最后设计 `external_task_ref`
   学“附属表”什么时候拆出去。

---

### 56. Codex

所谓 **Agent 开发**，你可以先别把它想得太玄。对实习岗位来说，它通常不是“训练大模型”，而是：

**把大模型接进业务系统里，让它能理解任务、调用工具、执行流程、保存结果、处理失败。**

所以 Agent 开发需要的技术栈，大概分成 5 层。

**1. 后端基础**
这是最重要的底盘。JD 里写 Agent，但很多公司实际还是在招能落地业务的人。

你需要会：
- Java / Python 至少一个主语言
- Spring Boot 或 FastAPI
- RESTful API
- MySQL / Redis
- 登录鉴权、参数校验、异常处理
- HTTP 调用第三方服务
- 日志和执行记录

你现在做的 `GameDev Agent Workbench` 其实正好覆盖这一层。

**2. LLM 调用能力**
Agent 的核心通常是调用大模型 API，而不是自己训练模型。

你需要理解：
- OpenAI / 通义 / DeepSeek / 智谱 / Claude 等 API 调用方式
- Prompt 设计
- System Prompt / User Prompt
- JSON 格式输出
- 流式输出 SSE
- Token、超时、重试、限流
- 多轮上下文管理

实习要求一般不会让你从零训练模型，但会希望你能把模型接到业务里。

**3. Tool Calling**
这是 Agent 和普通聊天机器人的区别之一。

普通聊天机器人：
- 用户问
- 模型答

Agent：
- 用户给任务
- 模型判断要不要调用工具
- 调接口、查数据库、查文档、提交任务
- 再把结果总结给用户

你需要理解：
- 什么是 Tool
- 工具参数怎么定义
- 模型如何选择工具
- 工具调用结果如何返回给模型
- 工具失败怎么处理
- 如何限制工具权限

比如你的项目里：
- Prompt 生成 Agent 可以调用旧项目 `AIGC-GameFlow`
- Bug 分析 Agent 可以分析日志
- 接口设计 Agent 可以生成 Apifox 结构

这些都可以包装成 Tool。

**4. Workflow / 执行编排**
很多 JD 写 Agent，其实更看重“AI 工作流”。

你需要理解：
- 一个任务分几步执行
- 每一步输入输出是什么
- 执行状态怎么保存
- 失败后能不能重试
- 执行记录怎么追踪
- 用户能不能查看历史结果

关键词一般有：
- Workflow
- Chain
- Trace
- Run
- Step
- Session
- Memory

你项目里的 `agent_run`、`agent_session`、`prompt_template` 就是这类能力的雏形。

**5. RAG / 知识库，属于常见加分项**
不是所有 Agent 岗都要求，但很多 JD 会写。

你需要知道：
- 文档切分
- Embedding
- 向量数据库
- 相似度检索
- 检索增强生成
- 召回和重排

常见技术：
- Milvus
- pgvector
- Elasticsearch
- FAISS
- LangChain
- LlamaIndex

但对你现在来说，RAG 可以先放后面。先把 Agent 调用闭环做出来更重要。

---

**JD 里常见词怎么翻译成人话**

- `Agent`：让大模型能调用工具、执行任务的系统
- `Tool Calling`：模型根据任务调用后端接口或函数
- `Function Calling`：Tool Calling 的一种形式
- `Workflow`：把 AI 任务拆成多个步骤执行

### 75. Codex

当然可以。我们先不写 SQL，就像老师带你做题一样，把“为什么要这样建表”讲清楚。

你现在要记住一句话：

**建表不是先想字段，而是先想业务里有哪些东西需要被长期保存。**

很多初学者一上来就问：“这个表要哪些字段？”  
但正确顺序应该是：

1. 这个系统发生了什么业务？
2. 哪些业务信息需要保存？
3. 哪些信息应该独立成表？
4. 表和表之间是什么关系？
5. 最后才是字段怎么设计。

---

**第一步：从业务流程里找数据**

你的 MVP 主流程是：

```text
用户登录
-> 用户发起 Agent 请求
-> Java 调 Python
-> Python 返回结果
-> Java 保存执行记录
-> 用户查看历史记录
```

我们从这条流程里找“必须保存”的东西。

这条流程里有两个最核心的对象：

- 用户
- Agent 执行记录

所以 MVP 第一阶段最少只需要两张表：

- `sys_user`
- `agent_run`

你看，这不是凭空想出来的，而是从业务流程里长出来的。

---

**第二步：判断一张表代表什么**

你可以把表分成几种类型。

### 1. 主体表

主体表存的是系统里的“角色”或“资源”。

比如：

```text
sys_user
```

它表示“谁在使用系统”。

用户不是一次行为，而是长期存在的主体，所以它应该单独成表。

### 2. 过程表

过程表存的是“发生过的一次事情”。

比如：

```text
agent_run
```

它表示“用户发起过一次 Agent 执行”。

这条数据不是一个静态对象，而是一条历史行为记录。  
过程表通常会保存：

- 谁做的
- 做了什么
- 输入是什么
- 输出是什么
- 成功还是失败
- 花了多久
- 什么时候发生的

你的 `agent_run` 就是典型过程表。

这点很重要，因为很多业务系统的核心其实都是过程表。订单表、支付表、日志表、任务表，本质上都是“某次行为”的记录。

---

**第三步：不要一开始把所有表都建出来**

你之前规划过 5 张表：

- `sys_user`
- `agent_session`
- `agent_run`
- `prompt_template`
- `external_task_ref`

但现在做 MVP，不一定要一次全做。

我们可以按优先级理解：

### MVP 必须有

`sys_user`  
因为你需要登录，需要知道是谁调用了 Agent。

`agent_run`  
因为你要保存每次 Agent 执行，这是项目主价值。

### 后面再有

`agent_session`  
用于多轮对话或会话归组。第一版如果只是一次请求一次结果，可以先不做。

`prompt_template`  
用于模板管理。第一版可以先把 prompt 写死在代码或 Python mock 里，后面再抽出来。

`external_task_ref`  
用于旧项目联动。第一版还不做真实联动，所以可以先不做。

这就是 MVP 思维：**先建支撑主链路的表，后面的表等业务真的需要时再加。**

---

**第四步：设计字段时，按 5 个问题来想**

每张表都可以用这 5 个问题推字段。

### 1. 这条数据是谁？

也就是主键。

通常是：

```text
id
```

如果这条数据需要对外暴露，还可以加：

```text
uuid
```

比如 `agent_run` 可以有 `run_uuid`，因为前端或 Apifox 查询详情时，用 UUID 比直接暴露数据库自增 ID 更安全、更稳定。

### 2. 这条数据属于谁？

比如 `agent_run` 是某个用户发起的，所以要有：

```text
user_id
```

这就是表之间的关系。

### 3. 这条数据的核心内容是什么？

对 `sys_user` 来说，核心内容是：

```text
username
password_hash
role
```

对 `agent_run` 来说，核心内容是：

```text
agent_type
input_text
output_text
```

### 4. 这条数据有没有状态？

很多业务表都有状态。

比如 `agent_run` 会有：

```text
status
```

可能取值：

```text
PENDING
RUNNING
SUCCESS
FAILED
```

状态字段的意义是：让系统知道这条记录现在处在哪个阶段。

### 5. 这条数据什么时候创建和更新？

几乎所有业务表都建议有：

```text
create_time
update_time
```

如果你做逻辑删除，再加：

```text
is_deleted
```

---

**第五步：用这个方法看 `sys_user`**

我们一问一答。

这张表是干什么的？

```text
保存系统用户。
```

它是主体表还是过程表？

```text
主体表。
```

它和谁有关？

```text
agent_run 会通过 user_id 关联它。
```

最少要存什么？

```text
用户名、密码、角色。
```

所以它自然会长出这些字段：

```text
id
username
password_hash
role
create_time
update_time
is_deleted
```

为什么要 `password_hash`，不是 `password`？

因为数据库里不应该存明文密码。  
后端收到密码后，要加密再存。

为什么要 `role`？

MVP 可以先只有 `USER`，但以后如果有管理员管理模板，就可以扩展 `ADMIN`。

为什么要 `is_deleted`？

以后删除用户时，不一定真的物理删除，可以逻辑删除，保留历史记录。

---

**第六步：用这个方法看 `agent_run`**

这张表是干什么的？

```text
保存每一次 Agent 执行记录。
```

它是主体表还是过程表？

```text
过程表。
```

它和谁有关？

```text
它属于某个用户，所以需要 user_id。
```

它最核心的内容是什么？

```text
用户输入、Agent 类型、Agent 输出。
```

它有没有状态？

```text
有。一次执行可能成功，也可能失败。
```

所以字段自然会变成：

```text
id
run_uuid
user_id
agent_type
input_text
output_text
status
duration_ms
error_msg
create_time
update_time
```

为什么要 `run_uuid`？

因为查询详情时可以用：

```http
GET /api/agent/runs/{runUuid}
```

这样前端不需要知道数据库自增 ID。

为什么要 `duration_ms`？

因为 Agent 项目很重视执行耗时。  
这就是 trace 的雏形。

为什么要 `error_msg`？

因为调用 Python 或 LLM 可能失败。  
失败原因必须保存，否则后面没法排查。

为什么 `input_text` 和 `output_text` 用 text 类型？

因为用户输入和模型输出通常比较长，不适合用短字符串。

---

**第七步：什么时候该拆表？**

这是表设计里很关键的能力。

你可以问：

**这个信息是不是每条记录都有？**

如果不是，就考虑拆表。

比如旧项目任务信息：

```text
external_task_uuid
external_status
external_result_url
```

不是每次 Agent 执行都有。只有 Prompt 生成并发送到旧项目时才有。

所以它不适合一开始塞进 `agent_run`，后面可以拆成：

```text
external_task_ref
```

再比如 Prompt 模板：

```text
template_name
template_content
enabled
version
```

它不是一次执行记录，而是系统配置。  
所以也不应该塞进 `agent_run`，而应该是：

```text
prompt_template
```

这就是拆表的基本判断。

---

**第八步：索引怎么想**

初学者常觉得索引很玄。你先记住一句话：

**经常用来查询的字段，才考虑加索引。**

比如 `sys_user`：

登录时要通过用户名查用户，所以：

```text
username
```

需要唯一索引。

比如 `agent_run`：

用户要查自己的历史记录，所以：

```text
user_id
```

需要索引。

用户可能按 Agent 类型筛选，所以：

```text
agent_type
```

可以加索引。

用户会按时间倒序看记录，所以：

```text
create_time
```

可以加索引。

如果一个字段只是展示用，不参与查询，就不用急着加索引。

---

**第九步：你现在设计表时最该避免什么**

### 1. 不要一开始做太多表

你现在 MVP 先做：

```text
sys_user
agent_run
```

就够了。

### 2. 不要为了“以后可能用”乱加字段

比如一开始就加：

```text
team_id
tenant_id
workflow_id
model_provider
token_cost
retry_count
```

不是不能加，而是 MVP 第一版不需要。

### 3. 不要把配置、过程、外部任务混在一张表里

这会导致表越来越乱。

### 4. 不要用中文字段名

数据库字段统一用英文下划线：

```text
create_time
agent_type
input_text
```

**第十步：你设计每张表时可以用这个模板**

以后你设计表，就先写下面这 6 行，不要急着写 SQL：

```text
表名：
业务含义：
表类型：主体表 / 过程表 / 配置表 / 关联表
和谁有关：
核心字段：
查询场景：
```

比如：

```text
表名：agent_run
业务含义：保存每次 Agent 执行记录
表类型：过程表
和谁有关：属于某个 sys_user
核心字段：user_id、agent_type、input_text、output_text、status、duration_ms
查询场景：按用户查询历史记录、按 run_uuid 查详情、按 agent_type 筛选
```

写到这里，你的表设计基本就清楚了。SQL 只是最后的翻译。

**最后总结一下**

你现在不要把建表理解成“写 SQL”。

你应该把它理解成：

**把业务里重要的人、东西、行为和状态保存下来。**

对于你的 MVP：

- `sys_user` 保存“谁在用”
- `agent_run` 保存“用户做过哪次 Agent 执行”

先把这两张表设计好，你就已经抓住项目数据库的核心了。下一步再考虑 `prompt_template`、`agent_session`、`external_task_ref`，会自然很多。
